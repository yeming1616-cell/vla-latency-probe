## 为什么做这个

我看过东南大学 PAISys 组的 [Embodied.cpp](https://github.com/SEU-PAISys/Embodied.cpp)（arXiv:2607.02501）——一个面向机器人 AI 的统一 C++ 推理运行时，首次同时支持 VLA 与 WAM 两类模型的边缘部署。

论文给出的两组数据让我停下来想了很久：

| 模型 | 动作块长度 | 每步延迟 |
|---|---|---|
| HY-VLA | 20 个动作 | 735.9 ms（每环境步摊销） |
| pi0.5 | 50 个动作 | **56.85 ms** |

论文把差异归因于骨干网络规模、视觉输入复杂度与动作块长度。这个解释我完全接受。**但我从中读出了另一点：动作块长度并不完全是模型自带的属性，它同时是一个可以主动选择的调度变量。**

- 动作块越短 → 闭环响应粒度越细，但单步推理开销摊薄得越少，算力压力越大；
- 动作块越长 → 单步成本被摊薄，但机器人对突发扰动的响应变迟钝，且一旦需要提前中断，已算出的块就被浪费。

而在"多速度同步运行"的前提下，这个问题更复杂：感知编码器可以每隔若干帧才刷新特征缓存，世界预测分支只在需要时激活，动作头却必须以更高频率持续产出。**各模块刷新频率、动作块长度、边缘设备算力预算，是互相耦合的自由度。**

所以我想先回答一个更基础的问题：

> **在真实硬件上，单步推理延迟的分布究竟长什么样？**

**平均值不够。** 实时系统里真正伤害控制质量的常常不是平均延迟，而是延迟的方差与尾部。两个平均延迟都是 60 ms 的实现，如果一个是 58–62 ms、另一个是 40–200 ms，对控制的影响完全不同。

这个仓库就是为了先把这件事测准。

## 里面有什么

### `latency_probe.py` —— 延迟与抖动测量

- 逐次调用、逐次计时，用 `time.perf_counter()`（单调高精度时钟）
- 报告 **均值 / 标准差 / min / max / p50 / p95 / p99**
- 额外报告**相邻调用间隔的标准差**（抖动指标）——这是均值看不出来的
- 写出行级原始数据 CSV，便于后续统计与对比
- **仅用 Python 标准库**，不需要 numpy / torch

```bash
# 先用内置合成负载验证测量链路
python latency_probe.py --runs 50 --warmup 5

# 接到自己的模型上
python latency_probe.py --runs 50 --model plugin:my_model:step --out results --label pi0.5-jetson
```

模型插件约定：模块里提供一个**无参数可调用对象**，执行一次推理。

```python
# my_model.py
def step():
    return model.infer(observation)
```

### `plot_hist.py` —— 延迟分布直方图

由 CSV 生成矢量 SVG 直方图（**同样只用标准库**，不依赖 matplotlib），并标出 p50 / p95 / p99 参考线。

```bash
python plot_hist.py results/latency.csv --bins 20
```

## 一次真实测量应该长什么样

我还没能在真实边缘设备上跑出数据——本机没有安装 Python 环境，也没有可用的边缘设备或 VLA 模型。**在拿到真实数据之前，我不会往这个仓库里放任何看起来像实验结果的图。**

计划中的第一次测量：

| 项目 | 计划 |
|---|---|
| 目标 | 单次 VLA 推理（或其中某个子模块）的延迟分布 |
| 自变量 | 动作块长度（例如 1 / 5 / 10 / 20 / 50） |
| 观测量 | 延迟 p50 / p95 / p99、gap_std（抖动） |
| 硬件 | 先在本机 CPU 跑通链路，再尝试 Jetson / 云 GPU |
| 预期 | 动作块变长会摊薄单步成本，但尾部延迟的形态如何变化，我还不知道 |
